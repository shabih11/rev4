# تشغيل rev4 وتطويره

## نطاق المنتج

المسار الأساسي: تسجيل الدخول ← نتيجة الشهر الحالي ← التفاصيل عند الطلب.
تتولى الإدارة تحديث البيانات وتصحيح التعيينات. تبقى الوظائف القائمة متاحة؛ الميزات الجديدة تعالج في مهام مستقلة.

## خريطة التعديل المختصرة

| الحاجة | نقطة البداية |
|---|---|
| عرض نتيجة الموظفة وحالة تحميلها | `src/components/EmployeeResults.tsx` |
| سجلات الموظفة والتنقل | `src/pages/EmployeeDashboard.tsx` |
| التسجيل والصلاحيات | `src/context/AuthContext.tsx` و`firestore.rules` |
| حساب النتائج الحالي | `enrichedUsers` في `src/context/DataContext.tsx` |
| طلب تفاصيل السجلات | `src/hooks/useRecordScope.ts` و`src/lib/cloudReadPlan.ts` |
| قراءة الملخص | `src/lib/dailyReadModel.ts` |
| تحديث المصدر وإعداد الملخص | `automation/README.md` |

## دورة البيانات الحالية

1. ملف العمل `.github/workflows/windsor-sync.yml` يحدد تحديثًا يوميًا الساعة 22:00 بالرياض وتشغيلًا يدويًا بنطاق تاريخ.
2. `automation/windsor-sync.mjs` يستورد تغييرات المصدر، ثم `automation/daily-read-model.mjs` يجهز ملخص العرض.
3. التطبيق يقرأ الملخص؛ تفاصيل التقييمات والشفتات تطلب عند فتح أقسامها.
4. الملخص مخزن في ذاكرة جلسة الصفحة. بعد نجاح إعداد ملخص جديد، أعيدي فتح الصفحة للحصول عليه؛ فتح السجل وحده لا يحدث الملخص.

وجود الملفات محليًا لا يثبت رفعها أو نجاح تشغيلها. راجعي نجاح خطوتي الاستيراد وإعداد الملخص في GitHub Actions. وقت إعداد الملخص لا يثبت نجاح استيراد المصدر؛ خطوة الملخص قد تعمل بعد فشل الاستيراد.
لا تضعي مفاتيح المصدر في الواجهة أو ملفات `VITE_*`. تفاصيل التفعيل والأسرار في `automation/README.md`؛ لا تنسخي قيمها إلى المحادثة.

## معايير قبول الإصدار

- الموظفة تسجل الدخول وترى نتيجة الشهر وتفاصيلها المسموح بها.
- انتظار الملخص أو فشله لا يظهر كأنه نتيجة صفرية؛ انتظار التفاصيل أو فشلها لا يظهر كأنه سجل فارغ.
- يظهر تاريخ إعداد الملخص عند توفره دون وصفه بأنه تاريخ آخر استيراد ناجح.
- التحديث المتكرر لا يكرر السجلات، ويحتفظ بتعيينات الموظفات والشفتات.
- الصلاحيات تختبر على قواعد Firestore؛ العرض في الواجهة وحده ليس إثباتًا لها.
- قبل تحديث جماعي يستبدل البيانات، تتحقق الإدارة من وجود نسخة احتياطية وطريقة استعادتها.

## تقليل استخدام Codex

- حددي نتيجة واحدة في كل مهمة، ونطاق الملفات ومعيار القبول إن كان معروفًا.
- استخدمي محادثة مستقلة للعمل غير المرتبط، مع ملخص قرارات قصير.
- في إعدادات Codex اختاري النموذج ومستوى التفكير وفق تعقيد المهمة، وعطلي التكاملات غير المستخدمة في بيئة العمل المعنية. لا تغيري إعدادات مشتركة تحتاجها مشاريع أخرى دون مراجعة أثرها.
- ابدئي بأسماء الملفات المتغيرة، ثم فروق محددة؛ لا تعرضي حذوفات الترحيل أو lockfiles كاملة.
- اعتمدي تغييرات متجانسة في التزامات منفصلة بعد مراجعتها؛ لا تضمي التعديلات المحلية السابقة تلقائيًا.
- قيسي الاستهلاك من واجهة الاستخدام لمجموعة مهام متقاربة قبل وبعد التغيير، مع عدد جولات الإصلاح ونتائج التحقق. حجم التعليمات يقيس تخفيف السياق ولا يساوي نسبة توفير الحصة.

## التحقق

للتعديلات البرمجية: `npm run lint` و`npm run build` مرة واحدة بعد اكتمال التغيير.
للمنطق المتغير: اختبارات مرتبطة فقط. للمسارات الحرجة: فحص محلي بحساب اختبار مأذون. لا تستخدم حسابات الإنتاج أو تشغل أدوات الترحيل الخاصة للتحقق.
