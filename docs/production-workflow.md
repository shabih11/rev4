# التحقق والإصدار

1. احفظ التعديلات المحلية غير المتعلقة بالمهمة دون ضمها إلى الالتزام. الهدف الافتراضي `main` وفق `AGENTS.md`؛ يُستخدم فرع آخر عند طلبه صراحةً.
2. اختر التحقق حسب الأثر كما في `AGENTS.md`: توثيق فقط يكفيه مراجعة الفرق؛ منطق محدود يحتاج الاختبار المرتبط وlint والبناء؛ تغييرات مشتركة تستعمل `npm run verify`. لا تكرر فحصًا ناجحًا دون تغيير مؤثر.
3. لتغييرات SQL والصلاحيات، شغّل بيئة الاختبار المحلية ثم `npm run test:db` كما في [دليل الاختبارات](testing.md). الاختبارات بمعاملات تُلغى؛ لا تستهدف الإنتاج.
4. راجع الفرق، وحدّث `main` من المستودع البعيد قبل الرفع. لا تستخدم force push ولا تضم أسرارًا أو بيانات استيراد خاصة.
5. يستخدم فحص الفروع وطلبات الدمج ومسار Pages ملف التحقق المشترك `.github/workflows/verify.yml`. يحدد `npm run check:scope` النطاق: التوثيق يتجاوز البناء والنشر؛ الصور وCSS تتجاوز المتصفح وSQL؛ منطق الواجهة يضيف المتصفح؛ البيانات والصلاحيات والأدوات تتطلب الفحص الكامل. التفاصيل في [دليل الاختبارات](testing.md).
6. الرفع إلى `main` ينشر التطبيق بعد نجاح الفحوص المطلوبة فقط. تُقارن التغييرات بآخر تشغيل ناجح، ويُستخدم الفحص الكامل إذا تعذر تحديد نطاق آمن أو عند التشغيل اليدوي. المتصفح وقاعدة الاختبار معزولان عن الإنتاج.
7. تحقّق من نتيجة GitHub Actions بعد الرفع؛ نجاح الفحوص المحلية لا يثبت نجاح النشر. نشر Pages لا ينشر هجرات Supabase أو Edge Functions تلقائيًا.

تفاصيل قاعدة البيانات: [عمليات Supabase](supabase-operations.md). مراجع Firebase في `docs/archive/` تاريخية.
