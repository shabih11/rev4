# اختبارات المشروع

المتطلبات العامة: Node.js 24 ثم `npm ci`.

## الفحص اليومي

ابدأ بالفحص المناسب للتغيير، لا بكل الأوامر أدناه. `npm run check:scope` يعرض نطاق الفحوص للملفات المعدلة، بما فيها الملفات الجديدة غير المتجاهلة؛ أضف `-- --staged` لفحص ما سيُحفظ فقط. الأمر يعرض النطاق ولا يشغّل الفحوص.

| التغيير | التحقق المحلي |
|---|---|
| التوثيق والتعليمات | مراجعة النص و`git diff --check` |
| صورة أو CSS أو نص واجهة | بناء واحد؛ فحص بصري محدد إذا تغيّر التخطيط |
| منطق أو مكوّن | lint والبناء والاختبار المرتبط |
| الدخول أو الحفظ أو الشفتات | ما سبق واختبارات المتصفح |
| SQL أو الصلاحيات | اختبارات SQL المعزولة، محليًا أو على CI |

`npm run verify` يجمع lint وجميع اختبارات Node وبناء TypeScript/Vite للتغييرات المشتركة بين عدة مجالات. لا تعِد تشغيله بعد نجاح الفحوص نفسها على نفس التغيير. مثال اختبار محدود: `node --test tests/dataActions.test.mjs`.

تستخدم اختبارات المكتبات أداة تحميل مشتركة في `tests/helpers/typescript.mjs` بدل تكرار محوّل TypeScript في كل ملف. بعض الاختبارات القديمة التي تحتاج محاكاة خاصة لم تُنقل بعد. اختبارات المتصفح تكمل اختبارات المنطق ولا تحل محلها.

## المتصفح

```sh
npx playwright install chromium
npm run test:browser
```

يمكن استخدام Chrome المثبت محليًا عبر `PLAYWRIGHT_CHANNEL=chrome npm run test:browser`. يشغّل Playwright خادم Vite مستقلًا على `127.0.0.1:4173`؛ يجب أن يكون المنفذ متاحًا.

تُختبر رحلة الدخول والخروج للأدوار الثلاثة، ورفض الحساب غير المخوّل وكلمة المرور غير الصحيحة، وإنشاء الشفت وإعادة قراءته وتعديل موظفاته ورفض الحفظ المتعارض. تعمل المكوّنات والمزوّدات الفعلية، وتُحاكى استجابات الخدمة ببيانات مصطنعة مع منع أي اتصال بإنتاج Supabase. وقت المتصفح ثابت لأجل الاختبار فقط؛ لا تتغير ساعة التطبيق المنشور. ملفات traces عند الفشل في `test-results/` المستبعد من Git.

## قاعدة البيانات المعزولة

يتطلب هذا الفحص Docker يعمل محليًا. تستخدم إعدادات `supabase/config.toml` مشروع الاختبار المحلي `rev4-tests`؛ لا تنفّذ `supabase link` لهذا الغرض.

```sh
npx --yes supabase@3.0.0 start -x studio,imgproxy,edge-runtime,logflare,vector,supavisor,mailpit
npm run test:db
npx --yes supabase@3.0.0 stop --no-backup
```

تُطبّق هجرات المستودع على القاعدة الجديدة، ثم تُنفّذ ملفات `supabase/tests/*.sql` مع إيقاف التنفيذ عند أول خطأ. كل ملف يستخدم `BEGIN / ROLLBACK`، ويُجهّز داخله إعداد كلمة مرور مصطنع في Vault ثم يُلغى معه؛ لا تُقرأ إعدادات الإنتاج. لا يقبل المشغّل عنوان اتصال أو مفاتيح إنتاج؛ يستهدف الحاوية المحلية `supabase_db_rev4-tests` فقط. أمر الإيقاف أعلاه يحذف بيانات بيئة الاختبار المحلية.

يُواءم المشغّل تواريخ الأربعاء/الخميس/الجمعة في `security.sql` مع الشهر المفتوح مع الحفاظ على الأيام المتتالية وحدود التوقيت، حتى لا يفشل فحص مديرة الفرع لمجرد انتقال الشهر. تواريخ الاختبار غير الصالحة وطوابع الدخول تبقى كما هي. اختبار الطلبات يستخدم تقييمًا بعد افتتاح الجمعة عند تشغيله يوم الجمعة. لا تتغير قواعد إغلاق الأشهر أو الصلاحيات في التطبيق.

## GitHub Actions

ملف `.github/workflows/verify.yml` مشترك بين فحوص الفروع وطلبات الدمج ونشر Pages، ويختار النطاق عبر `automation/check-scope.mjs`:

- التوثيق فقط (`README.md` و`AGENTS.md` وملفات Markdown في `docs/`): لا تثبيت تبعيات أو بناء أو نشر.
- صور وخطوط `src/assets/` و`public/` وCSS: lint واختبارات Node والبناء؛ بلا تجهيز Chromium أو Supabase.
- كود الشاشات والمكوّنات و`App.tsx` و`main.tsx` واختبارات المتصفح: تُضاف اختبارات Chromium.
- منطق البيانات المشترك وhooks والأنواع وSQL وأدوات البناء والتبعيات والفئات غير المعروفة: الفحوص الكاملة، بما فيها SQL المعزول. تغييرات اختبارات Node وحدها لا تشغّل الخدمات الثقيلة، باستثناء اختبار مصنّف الفحوص نفسه.

في الرفع تُقارن النسخة بآخر تشغيل ناجح لنفس workflow والفرع، حتى لا يتجاوز تعديل لاحق فحوص تغيير سابق أُلغي أو فشل. في طلب الدمج تُقارن بقاعدة الطلب. إذا غابت النسخة المرجعية من السجل المتاح أو تعذر جلبها، تُشغّل الفحوص الكاملة. الحذف وإعادة التسمية محسوبان من طرفيهما. التشغيل اليدوي من GitHub يشغّل الفحص الكامل دائمًا.

لا يبدأ النشر إلا بعد نجاح الفحوص المطلوبة ووجود تغيير يتطلب بناءً. يبقى تعطيل الفحوص غير المتعلقة بالتغيير مختلفًا عن فشل فحص مطلوب؛ الفشل يمنع النشر.
