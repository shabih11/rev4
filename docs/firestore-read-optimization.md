# مراجعة تقليل قراءات Firestore

التاريخ: 2026-10-19 — مشروع rev4، قاعدة Firestore Standard الحالية.

## سبب التغيير

كان DataProvider يبدأ ستة اشتراكات مباشرة لكل جلسة، بما فيها جميع التقييمات
التفصيلية والمناوبات، حتى عند عرض لوحة الترتيب فقط. أغلب الاستعلامات لم تكن
تحدد الفرع أو الموظفة. الرسم الذي عُرض في المحادثة لا يحدد المصدر الدقيق
لكل قراءة؛ لم تُنسب قراءات الإنتاج إلى استعلام معين دون قياسات Query Insights.

## الاستعلامات بعد التعديل

| الشاشة | التقييمات التفصيلية | المناوبات والأحداث التفصيلية |
|---|---|---|
| الترتيب عند الفتح | لا طلب | لا طلب |
| تفاصيل موظفة | المرتبطة بمعرّفها أو اسمها | نطاق الموظفة للإدارة؛ نطاق الصلاحية الحالي للحسابات الأخرى |
| تفاصيل فرع | الفرع المفتوح | عند اختيار يوم لعرض الفريق، ضمن صلاحية الحساب |
| لوحة الموظفة | تقييماتها فقط | نطاق الموظفة المفروض بالقواعد الحالية |
| لوحة مديرة الفرع | الفرع الحالي | الفرع الحالي |
| إدارة النظام: الشفتات والإحصاءات | الفرع المعروض | الفرع المعروض |
| إدارة النظام: الموظفات أو الفروع | لا طلب، إلا عند فتح الدمج | لا طلب، إلا عند فتح الدمج |
| الدمج أو استيراد Windsor | كامل السجل | كامل السجل |

اشتراكات الدليل والفروع وملخصات التقييمات والملاحظات تبقى مشتركة في DataProvider.
النطاقات المتزامنة تُجمع باستعلام OR موحّد دون تكرار النتائج، ويُلغى الاشتراك
التفصيلي عند زوال الطلب عليه. الاستعلامات متكافئة النطاق لا يعاد تشغيلها
بسبب إعادة عرض React وحدها.

الاستيراد التلقائي المفعّل صراحة يحتاج كامل البيانات للمقارنة والربط، ولذلك
يُبقي النطاق الكامل محمّلًا. مؤقته يستخدم أحدث دالة مزامنة دون إعادة إنشائه
مع كل تغير في البيانات.

## تقليل الكتابات والقراءات التابعة لها

- تعديل تعليق تقييم لا يعيد كتابة reviewSignals إذا لم تتغير حقول النقاط والربط.
- تعديل نص ملاحظة لا يعيد كتابة noteSignals إذا لم يتغير ملخصها.
- تعديل البريد أو حقل خاص لا يعيد كتابة profiles إذا لم يتغير الملف العام.
- التغييرات المؤثرة في النقاط والروابط تُحدّث الملخصات في دفعة الحفظ نفسها.

## المراجعة الأمنية وصحة البيانات

المراجعة مركزة على التغييرات الجديدة في مزامنة البيانات وتسجيل نطاقات الشاشات.
راجعت تاريخ cloudSync في 3f1345d ومستهلكيه المباشرين: DataProvider وخمس شاشات
أو مكونات تستخدم طلب التفاصيل. التعديلات المحلية السابقة في القواعد وكلمات
المرور وغيرها خارج نطاق هذه المراجعة، وقد حُفظت كما كانت عند بدء المهمة.

- لم تُعدّل قواعد Firestore أو يُخفف تفويض الخادم في هذه المهمة.
- استعلامات timeline للمديرات والموظفات تحتفظ بقيد الفرع أو معرّف الموظفة.
- النطاق الفارغ يعطل الطلب؛ تجاوز حدود OR يعطي خطأ بدل توسيع الطلب أو اقتطاعه.
- تبديل النطاق أو الحساب يخفي السجلات القديمة فورًا، وتُهمل نتائج الاشتراكات السابقة.
- لقطة الذاكرة المؤقتة وحدها لا تتيح الكتابة؛ يلزم تأكيد الاستعلام من الخادم.
- الدمج والاستيراد والمسح الشامل ينتظرون اكتمال النطاق الكامل قبل التنفيذ.
- تغيير الشاشة لا يلغي دفعة حفظ بدأت بالفعل للحساب نفسه. تغير جلسة الحساب
  أو هوية Firebase الفعلية يمنع إرسال الدفعات التي لم تُرسل بعد.
- حذف عنصر من نتيجة مقيدة لا يحذف وثائق لم تُجلب في ذلك النطاق.

لم تظهر مشكلة أمنية غير معالجة في الفرق الذي راجعته. ذلك لا يعادل تدقيقًا
شاملًا للتطبيق أو اختبارًا لقواعد الإنتاج.

## التحقق والحدود

- نجح lint والبناء؛ تبقى تحذيرات Fast Refresh وحجم الحزمة المعروفة.
- اختبارات تخطيط الطلبات والمزامنة تغطي تعطيل الاستعلام، دمج النطاقات، تبديل
  النطاق، تجاهل اللقطات القديمة، الحفظ من ذاكرة مؤقتة، تبديل الهوية، وحماية الحذف.
- اختُبرت صلاحية تركيب OR بواسطة Firebase SDK الحقيقي دون إرسال استعلام شبكي.
- اختبارات Windsor وتنسيق التاريخ نجحت أيضًا.
- فُحصت الفروق من الفراغات الزائدة. لم تُستخدم حسابات حقيقية لاختبار رحلة واجهة،
  ولم تُقرأ أو تُكتب بيانات الإنتاج، ولم تُنشر نسخة التطبيق في هذه المهمة.
- لا توجد نسبة توفير مقاسة بعد النشر. التخفيض الفعلي يتوقف على حجم كل مجموعة
  وعدد المستخدمين والنوافذ وإعادة الاتصال.

لم تُقتطع السجلات التاريخية بحد عشوائي؛ الإجماليات والشراكات والنقاط تحتاج
التاريخ الكامل لملخصات التقييمات. خفض هذه القراءات أكثر يتطلب ملخصات مجمعة
موثوقة على الخادم مع ترحيل واختبار البيانات، أو إعادة تصميم الشاشات التاريخية
لتصفح صفحات مستقلة عن عمليات تعديل القوائم. ليس هذا ضمن التغيير المحلي الحالي.
