# مراجعة دمج الواجهة مع Supabase

## النطاق

الأساس هو `origin/main` عند `c842789`، على الفرع `codex/supabase-ui-merge`. تاريخ الفرع المحلي السابق مستقل؛ لذلك اعتمدت نسخة GitHub حسب اختيار المستخدم ونقلت ميزات الواجهة إليها بدل دمج ملفات Firebase مع Supabase آليًا.

حُفظت التعديلات الأصلية في stash باسم `Local UI before Supabase integration 2026-10-22`، ونسخة ملفات عامة قابلة للاسترجاع في `/tmp/rev4-local-ui-before-supabase-epx4uhn2`. البيانات الخاصة والبيئة وملفات scripts وreports ليست ضمن النسخة المنقولة إلى الفرع الجديد.

## النتيجة

- بقي Supabase Auth وRLS وRPC والمزامنة ومعالجة تعارض الحفظ من النسخة الرئيسية.
- بقيت تحسينات GitHub للهوية والموبايل وتقسيم الحزم والتحميل.
- نُقل التقويم الموحد، التذكير خلال آخر ثلاثة أيام بتوقيت الرياض، قرار المديرة والتصعيد لمدة 72 ساعة من الرفض.
- نُقلت بطاقات الموظفات وتنسيق الأزرار وخط Cairo وتعديلات النصوص وتحميل التعليقات الكاملة.
- استُبدلت اتصالات Firebase في رقم الإدارة وطلبات الدمج باتصالات Supabase.
- الشفتات المشتركة تستخدم سياسة RLS المضافة مسبقًا في GitHub؛ الملاحظات الخاصة تحتفظ بصلاحياتها.

## مراجعة الأمان المحددة

الهجرة الجديدة تضيف metadata لطلبات الشفت إلى التحقق الحالي دون إزالة فحوص الفرع أو الهوية أو تداخل الشفتات أو إغلاق الأشهر. الأسماء تُؤخذ من ملف الموظفة الموثوق، والمهلة تُحسب في PostgreSQL، ووقت الرفض يُختم في الخادم. الفهرس الفريد يمنع الطلبات المفتوحة المتكررة حتى عند التزامن. قبول الطلب يتطلب شفتًا يحتوي الموظفة عند نهاية المعاملة؛ الربط مع التقييمات يتم عبر trigger الموجود في GitHub.

جدول رقم الإدارة يقرأه الأعضاء النشطون ويكتبه السوبر أدمن فقط. طلبات دمج الحسابات يراها مدير الفرع والسوبر أدمن، ويغلقها السوبر أدمن فقط. إنشاء موظفة بواسطة المديرة محدود بفرعها وملف فارغ من الأرصدة دون منح حساب دخول أو صلاحيات. لم تُضف دوال SECURITY DEFINER جديدة أو مفاتيح سرية إلى العميل.

نطاق الاستدعاء: واجهتان للتذكيرات ورقم الإدارة، واجهتا إدارة الموظفات، ومسار قبول واحد في DataContext. لم تظهر مشكلة صلاحيات مؤكدة في الفحوص المحددة، وهذا ليس تدقيقًا كاملًا للمشروع.

## التحقق والحدود

- نجح build وlint؛ تحذيرا Fast Refresh باقِيان من نمط تصدير السياق.
- نجحت اختبارات المشروع الـ36.
- شُغلت جميع الهجرات في PostgreSQL مؤقت عبر PGlite داخل `/tmp`، ثم نجحت اختبارات SQL: `security.sql` و`shared_records.sql` و`shift_requests.sql`، وجميع بيانات الاختبارات اصطناعية وتُلغى بـROLLBACK.
- اختبار SQL يغطي انتحال الاسم، المهل، تكرار الطلب، قبول النفس، منع القبول دون شفت، الربط الذري للتقييمات، رقم الإدارة، خصوصية طلبات الدمج وإنشاء موظفة خارج الفرع.
- هذا تحقق PostgreSQL محلي، وليس اختبار Supabase Auth أو Realtime كاملًا.
- محاولة اختبار المتصفح تعذرت لأن ملف متصفح Playwright مستخدم بجلسة أخرى؛ لم تُغلق تلك الجلسة ولم تُستخدم بيانات دخول حقيقية.
- npm ci استخدم lockfile القادم من GitHub وأبلغ عن 7 ثغرات اعتماديات (2 متوسطة، 5 عالية). لم تُغيّر الإصدارات ضمن الدمج.

## التفعيل

طُبقت الهجرة `supabase/migrations/20261022055911_local_ui_shift_requests.sql` على المشروع بعد موافقة المستخدم الصريحة، وطابق اسم الملف رقم الهجرة المسجل في Supabase. تحقق القراءة قبل التطبيق أكد غياب الجداول الجديدة، ثم أكّد التحقق بعد التطبيق وجود دالة الدمج الجديدة. لا حاجة لاستيراد بيانات Firebase لتفعيلها.

## اختيار الحسابات ووسم التغطية

اختيار الحساب الأساسي والمكرر أصبح على خطوتين: الفرع ثم الموظفة، مع مسح الموظفة عند تغيير الفرع واستبعاد الحساب الأساسي من قائمة المكرر. وسم التغطية أصبح اختيارًا صريحًا `isCoverage` مستقلًا عن `assignedBranches` التاريخية؛ إزالة الوسم لا تحذف ارتباطات الشفتات السابقة. RPC جديد `merge_employees_with_coverage` يتحقق من دور admin ويجمع الدمج وتغيير الوسم في معاملة واحدة، دون دوال SECURITY DEFINER إضافية. طلب المديرة يحفظ اختيار الوسم لتراجعه الإدارة. تم تضمين هذا التحديث في الهجرة المطبقة.

اجتاز التحديث build وlint واختبارات PostgreSQL الثلاثة. أضيف تحقق فعلي لإزالة الوسم مع بقاء الفرع التاريخي ثم إعادة تفعيله عبر عمليتي دمج اصطناعيتين داخل اختبار يُلغى بـROLLBACK. لم يُختبر التدفق بحساب متصفح.
