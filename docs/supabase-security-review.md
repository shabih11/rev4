## حدود الثقة التي روجعت

1. مهاجم غير مسجل: محاولة قراءة الجداول وRPC أو استدعاء الاستيراد دون توقيع. رفض RLS/API و401 للوظيفة مؤكد فعليًا.
2. موظفة مسجلة: تزوير `user_metadata.role=admin`، وقراءة البريد، وتعديل الدور أو دمج الأسماء. رُفضت في SQL؛ صلاحية الدور تُقرأ من عضوية حديثة لا ادعاء قابل لتعديل المستخدم.
3. مديرة فرع: قراءة السجلات خارج الفرع أو إدخال موظفة غير مخولة أو شفت متداخل. سياسات RLS والتحقق الخادمي تمنعها؛ اختبار الشهر المفتوح وحدود الشفت والرياض مؤكد.
4. جهة خارج workflow: تزوير الفرع أو المستودع أو الحدث أو الجمهور أو التوقيع أو العمر. اختبارات JWT بمفاتيح RS256 فعلية تغطي الرفض، والتوقيع يُفحص عبر GitHub JWKS في الإنتاج.
5. كتابة متزامنة: `write_rows` يقارن النسخة تحت القفل ويعيد 40001 عند التعارض. حفظ المصدر يحتفظ بتعيينات الصف المقفول؛ لا يعتمد على لقطة التعيين السابقة، ويعيد الربط إذا تغير وقت المصدر. تحديث المرآة وإصدار البيانات داخل المعاملة.
6. تغيير فرع شفت: تعاد حسابات الفرعين القديم والجديد. دمج الموظفات مقيد بالإدارة وينقل العضويات والارتباطات ذريًا قبل حذف المكرر.
7. تسرب مفاتيح: مفتاح Supabase في العميل publishable فقط. Windsor سر GitHub، ومفتاح الإدارة داخل Edge Runtime فقط. السجلات تعرض أعدادًا؛ لا مصادر خام أو JWT أو كلمات مرور.
8. نشر خاطئ: فرع Supabase لا ينشر Pages. مرجع workflow المسموح محدد، وأذونات GitHub للقراءة وOIDC فقط. أدوات checkout/setup-node مثبتة بـ SHA.

## تنبيهات مقصودة وحدود قائمة

أبلغ Supabase عن أربع وظائف `SECURITY DEFINER` متاحة لـ authenticated: `get_my_account` لحساب الجلسة وحده، و`get_read_model` لملخص الأعضاء المنقح، و`get_accounts` و`merge_employees` للإدارة فقط. كلها تسحب الصلاحيات من `user_access`، وتستخدم `search_path=''`، وتمنع PUBLIC/anon. اختبار الرفض للحساب بلا عضوية وللموظفة والمديرة مكتمل. هذه واجهات عامة مقصودة ذات تحقق داخلي، لذا يبقى [تنبيه Supabase](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable) موثقًا.

حماية كلمات المرور المسربة غير مفعلة في إعدادات Auth، ولم تتوفر أداة MCP لتغيير هذا الإعداد. حساب المدير أنشئ بكلمة عشوائية قوية، لكن ذلك لا يعوض [تفعيل فحص الكلمات المسربة](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection) للحسابات اللاحقة إذا أتاحته الخطة.

بعد تحديثات متوافقة للاعتماديات، `npm audit --omit=dev` يعرض صفر ثغرات. بقيت 7 تنبيهات في سلسلة أدوات Tailwind 3، وإصلاحها الآلي يتطلب الانتقال الكبير إلى Tailwind 4؛ لم يُنفذ ترحيل واجهة خارج النطاق. البناء يعرض تحذير حجم الحزمة (~843 kB، ~240 kB gzip)، وlint يعرض تحذيري Fast Refresh سابقين.

## أدلة التحقق وحدوده

- 27 اختبار Node ناجح؛ منها التخزين وعزل النطاق وتشارك الطلبات والترقيم والتطبيع وOIDC.
- lint وبناء Vite/TypeScript ناجحان؛ لا ادعاء بأن التحذيرات اختفت.
- SQL فعلي داخل BEGIN/ROLLBACK: عزل الأدوار، منع التسريب والتصعيد، نصف الفاصل الزمني، عبور منتصف الليل، التعارض، تعديل الاسم، الدمج، وحفظ ربط المصدر وتصحيح وقته.
- Supabase SDK: مصادقة المدير ودوره وملخصه وحساب إداري واحد وستة فروع؛ قراءة مجهولة مرفوضة.
- رحلة Chrome محلية بحساب المدير الجديد: دخول، تحميل الإعدادات الصحيحة، الفروع والموظفات، ثم تكرار التنقل بصفر قراءات إضافية وصفر أخطاء JavaScript.
- إنشاء المدير تم عبر Auth Admin API بوظيفة مؤقتة برمز عشوائي ومدة محدودة، ثم استبدلت بنسخة مغلقة تتطلب JWT. بيانات الدخول في ملف محلي خاص غير متعقب.
- لا توجد رحلة UI حقيقية لموظفة/مديرة بعد؛ يتطلب ذلك الحقن اللاحق. لم يتغير الموقع الحي أو `main` ضمن إعداد الفرع.
